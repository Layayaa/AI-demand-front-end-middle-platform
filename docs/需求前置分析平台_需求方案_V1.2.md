# 需求前置分析平台 · 需求方案 V1.2

> 版本：V1.2　状态：评审版　编制日期：2026-08-20  
> 面向对象：业务部门、业务负责人、产品/数字化、技术团队  
> 产品定位：让业务先把需求讲清楚，再决定是否做、怎么做、何时做。
>
> 当前实现口径（2026-08-24）：先生成 1 份《需求解释方案》；评审人确认后，再生成半自动/简单版、全自动/复杂版两档解决方案，每档产品版 + 技术版，共 4 份解决方案。下文早期三档方案描述仅保留作历史背景，不作为当前验收口径。

## 1. 本次更新

V1.2 基于原始诉求和 V1.1 评审结果，明确以下产品闭环：

1. 业务人员直接用自然语言提交需求，不要求先写专业文档。
2. AI 在立项前通过对话补齐场景、目标、数据、规则、边界和验收口径。
3. 需求完成澄清后，生成初级、中级、高级三档方案。
4. 每档方案均拆成产品版和技术版，共 6 份文档。
5. 平台持续反馈当前进度，并对需求做价值、优先级和投入产出分析。

与 V1.1 的关键调整：初级方案不再是产品与技术合并速览，而是拆为初级产品版和初级技术版，三档统一遵循“双版本交付”。

## 2. 背景与问题

业务部门常见的提需方式是“想做一个自动化”“希望有个系统支持一下”，但缺少：

- 要解决的真实业务问题和目标结果；
- 当前流程、判断规则、数据来源和人工耗时；
- 哪些边界必须由人处理，哪些步骤可以自动化；
- 需求的业务价值、紧急程度和影响范围；
- 业务、产品、技术对同一需求的统一理解。

因此，需求进入产品或技术阶段后容易反复澄清，方案深度不一致，排期依赖经验，业务也无法知道需求当前进展。

## 3. 建设目标

### 3.1 产品目标

建设一个面向业务部门的需求前置分析网站，形成：

```text
提交需求
  → AI 前置澄清
  → 结构化需求画像
  → 三档六文档方案
  → 价值与优先级分析
  → 进度反馈与业务评审
```

### 3.2 预期收益

| 目标 | 预期结果 |
| --- | --- |
| 降低提需门槛 | 业务只需描述场景，AI 负责补齐结构化信息 |
| 减少沟通返工 | 需求在进入开发前完成数据、规则、边界和验收口径确认 |
| 统一方案质量 | 所有需求按统一模板生成产品版和技术版 |
| 支持投入决策 | 用统一评分回答“先做哪个、投入多少、风险多大” |
| 提升过程透明度 | 业务可查看澄清、分析、方案、评审的实时状态 |

## 4. 用户与角色

| 角色 | 核心诉求 | 主要操作 |
| --- | --- | --- |
| 业务提需人 | 不会写 PRD，也能把想法讲明白 | 创建需求、参与 AI 对话、确认画像 |
| 业务负责人 | 判断是否值得投入 | 查看价值分析、评审方案、确认优先级 |
| 产品/数字化顾问 | 快速获得完整需求输入 | 复核画像、查看产品版、补充范围和验收 |
| 技术负责人 | 快速判断可行性和投入 | 查看技术版、确认数据接入、风险和排期 |
| AI 需求顾问 | 发现关键信息缺口 | 追问、提取画像、生成方案、解释评分 |

## 5. 产品范围

### 5.1 本期范围

- 需求提交和需求列表；
- AI 前置澄清对话；
- 单点决策 / SOP 流程自动识别；
- 结构化需求画像和完整度反馈；
- 初级、中级、高级三档方案；
- 每档产品版、技术版两份文档，共 6 份；
- 文档在线查看、Markdown 下载、Word 下载；
- 需求状态和进度时间线；
- AI 价值评分、P0/P1/P2 优先级和投入评估；
- 可插拔知识库挂载架构（默认关闭，支持本地目录、RAGFlow 和通用 HTTP 检索服务）；
- 业务评审和确认完成；
- 内置规则引擎与可选大模型模式。

### 5.2 本期不做

- 多组织、多租户和复杂权限体系；
- 移动端原生应用；
- 自动替业务完成实际业务操作；
- 未经确认的跨系统深度改造；
- 企微、飞书、钉钉消息闭环；
- 大规模向量化检索、复杂权限和企业历史需求自动学习。

## 6. 核心业务流程

### 6.1 端到端流程

```text
业务提交名称、描述、部门
  ↓
AI 自由对话，识别需求形态并补齐关键事实
  ↓
形成需求画像，显示完整度和待确认项
  ↓
业务确认画像
  ↓
生成初级/中级/高级 × 产品版/技术版，共 6 份
  ↓
AI 生成价值分、优先级、工作量、风险和置信度
  ↓
业务负责人评审，补充或确认
  ↓
进入需求优先级看板，支持后续排期
```

### 6.2 AI 对话原则

- 允许业务自由描述，不强制先理解“单点决策”和“SOP”等术语；
- AI 一次只问一个关键问题；
- 用户一次回答多项信息时，AI 自动拆分并归入画像；
- AI 不重复追问已经明确的内容；
- 缺失信息显示“待确认”，不为了完整而虚构；
- 大模型不可用时，降级到内置规则引擎，流程不中断；
- 画像达到可交付条件后，AI 先总结并请求业务确认。

## 7. 功能需求

### FR1 需求提交

业务填写：

- 需求名称，必填，最多 60 字；
- 一句话描述，可选，最多 300 字；
- 所属部门，可选。

提交后生成需求编号，状态为“已提交”，系统自动进入 AI 前置澄清。

### FR2 AI 前置澄清

AI 需要至少覆盖以下信息：

| 需求类型 | 必须澄清的信息 |
| --- | --- |
| 单点决策 | 决策目标、频率、价值、影响维度、耗时、参与人、输入数据、来源系统、取数方式、分析规则、判断标准、对应行动 |
| SOP 流程 | 流程目标、频率、价值、影响维度、耗时、参与人、步骤、输入、触发、处理类型、输出、来源系统、取数方式、人工原因 |

对话结束条件：

- 画像完整度达到可交付门槛；
- 或业务主动确认使用“待确认”项生成方案；
- 或业务明确要求跳过澄清。

### FR3 需求画像

画像右侧实时展示：

- 已识别的需求类型；
- 基本信息；
- 已确认字段；
- 数据来源和取数方式；
- 规则、判断标准或流程步骤；
- 缺失字段；
- 画像完整度；
- AI 当前澄清阶段。

### FR4 三档六文档方案

三档方案不是三份不同长度的同文档，而是三种投入决策深度；每档均提供产品版和技术版。

| 档位 | 产品版 | 技术版 | 适用决策 |
| --- | --- | --- | --- |
| 初级 | 需求价值、目标、首期范围、关键用户结果、验收口径、建议决策 | 数据可得性、自动化潜力、初步技术路径、工作量粗估、技术边界、主要风险 | 值不值得做、能不能快速试点 |
| 中级 | 背景目标、范围、改造流程、功能清单、角色、验收标准、建议排期 | 取数方案、自动化实现、系统集成、工作量、排期、技术风险和依赖 | 是否进入正式评审、怎么做 |
| 高级 | 完整 PRD、用户角色、流程、功能详设、数据字典、异常边界、KPI、里程碑 | 总体架构、数据流、详细设计、非功能需求、实施计划、风险、回退方案 | 是否立项、如何完整落地 |

文档要求：

- 每份文档注明需求编号、档位、文档类型、生成时间和 AI 模式；
- 所有未知项标记“待确认”；
- 产品版和技术版引用同一份需求画像，避免口径分叉；
- 支持在线查看、Markdown 下载、Word 下载；
- 文档生成后状态自动进入“待业务评审”。

### FR5 进度反馈

状态流转：

```text
已提交 10%
  → AI 前置澄清中 35%
  → 画像分析中 55%
  → 需求画像完成 65%
  → 方案生成中 75%
  → 待业务评审 90%
  → 已完成 100%
```

每次状态变化记录：

- 状态；
- 变化时间；
- 触发动作；
- 备注；
- 当前负责人或参与角色。

### FR6 价值优先级分析

AI 基于画像计算 0-100 分：

| 维度 | 权重 | 说明 |
| --- | ---: | --- |
| 价值大小 | 35 | 收入、成本、客户、风险等业务影响 |
| 发生频率 | 15 | 每天、每周、每月等发生频次 |
| 耗时投入 | 15 | 单次耗时和参与人数 |
| 影响维度 | 12 | 影响部门、客户、收入、成本或合规 |
| 自动化潜力 | 15 | 数据和规则是否适合自动化 |
| 参与人数 | 8 | 参与范围越大，协同收益越高 |

优先级规则：

- P0：80-100 分，建议立即做；
- P1：60-79 分，建议纳入本季度计划；
- P2：0-59 分，建议补充信息、暂缓或合并。

输出必须包含：

- 总分和优先级；
- 每个维度的得分；
- 评分依据；
- 推荐下一步；
- 画像缺口；
- 预估工作量；
- 规模、风险等级和置信度。

AI 评分是决策辅助，不替代业务负责人最终拍板。

## 10. 知识库挂载架构

知识库采用“业务主流程 + 可选上下文层”的架构。知识库默认关闭，未启用时，提需、澄清、方案生成和价值评分保持原有行为。

### 10.1 接入原则

- 核心业务只依赖统一的 `search(query)` 接口，不依赖某一个 RAG 厂商；
- 本地目录 Provider 用于开发和小规模试点，零依赖读取 Markdown、文本和结构化文本；
- RAGFlow Provider 调用标准检索接口，适合后续接入向量检索、重排和引用；
- 通用 HTTP Provider 允许接入公司已有知识库服务；
- 检索失败、超时或没有命中时，AI 继续使用需求画像完成主流程；
- 知识库只能提供背景参考，业务本轮明确描述优先级高于知识库内容；
- 方案引用知识库内容时应保留来源文件名或来源标识。

### 10.2 上下文流转

```text
业务输入 / 需求标题 / 需求画像
  ↓
Knowledge Provider.search(query)
  ↓
统一结果：source / title / text / score
  ↓
上下文裁剪与来源标记
  ↓
AI 澄清追问 / 画像自检 / 六份方案生成
```

### 10.3 Provider 配置

| Provider | 主要配置 | 适用场景 |
| --- | --- | --- |
| local | 本地挂载目录、TopK、上下文长度 | 零依赖开发、少量内部资料 |
| ragflow | Base URL、Dataset ID、API Key | 已有 RAGFlow 知识库 |
| http | 检索地址、API Key、Dataset ID | 公司自建检索服务或其他 RAG 平台 |

通用 HTTP Provider 默认请求：

```json
{ "query": "需求方案", "topK": 5, "datasetId": "optional" }
```

响应可返回 `results`、`chunks`、`records` 或 `items` 数组，片段使用 `text` / `content`，来源使用 `source` / `title` / `document_name`。

### 10.4 暂不纳入本期

- 文档上传、解析、切片、向量化和重排管理后台；
- 多用户知识库权限；
- 自动同步企业网盘、对象存储和消息系统；
- 知识库内容自动修改需求画像；
- 以知识库结果替代业务确认和技术评审。

## 11. 非功能要求

| 类别 | 要求 |
| --- | --- |
| 易用性 | 业务无需培训即可提交需求和完成澄清 |
| 性能 | 内置引擎生成 6 份文档目标小于 5 秒；大模型模式给出等待提示 |
| 可靠性 | LLM 超时、报错或未配置时自动回退内置引擎 |
| 可解释性 | 价值分、优先级和方案结论都能追溯到画像字段 |
| 数据安全 | API Key 不进入前端；未知信息不得被模型虚构 |
| 文档兼容 | Markdown 和 Word 可正常打开、下载和归档 |
| 可维护性 | 提取、澄清、方案、价值、文档导出模块解耦 |

## 12. 验收标准

| 编号 | 场景 | 验收标准 |
| --- | --- | --- |
| A1 | 提交需求 | 业务提交后 1 秒内进入工作台，AI 欢迎语出现 |
| A2 | 前置澄清 | AI 能识别单点决策或 SOP，并显示画像完整度 |
| A3 | 画像确认 | 已确认内容正确落入画像，缺失内容显示“待确认” |
| A4 | 六文档生成 | 初/中/高级各生成产品版和技术版，共 6 份 |
| A5 | 版本一致 | 6 份文档引用同一份画像，产品版和技术版口径一致 |
| A6 | 文档交付 | 6 份文档可在线查看，并可下载 Markdown、Word |
| A7 | 进度反馈 | 状态按流程自动推进，时间线可追溯 |
| A8 | 价值分析 | 输出分数、P0/P1/P2、依据、工作量和风险 |
| A9 | 业务评审 | 业务可继续澄清、重新生成方案或确认完成 |
| A10 | 兜底 | 无模型密钥或模型失败时，内置引擎仍可完成主流程 |

## 13. 实施建议

| 阶段 | 内容 | 结果 |
| --- | --- | --- |
| M1 | 需求提交、澄清、画像和进度 | 业务能完成一次完整提需 |
| M2 | 三档六文档、在线查看和下载 | 产品与技术都有可评审材料 |
| M3 | 价值优先级、投入评估和看板 | 支持需求排序和排期决策 |
| M4 | 小范围试点 | 选 2-3 个真实需求验证返工率和满意度 |
| M5 | 多用户、权限、消息和知识库 | 从单机工具升级为组织平台 |

## 14. 成功指标

- 需求画像平均完整度不低于 85%；
- 单条需求 AI 澄清耗时不超过 15 分钟；
- 6 份方案文档自动生成耗时不超过 5 分钟；
- 需求评审一次通过率较上线前提升 30%；
- 方案返工率下降 50%；
- 业务使用满意度不低于 4/5。

---

本方案以“让业务说清楚、让产品能评审、让技术能落地、让管理者能排序”为验收主线。
