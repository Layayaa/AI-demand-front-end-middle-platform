## 1. 项目背景与目标

### 1.1 背景

业务部门（商品运营、客服、采购等）在日常工作中存在大量**重复性决策与流程**：判断滞销 SKU 该降价还是清仓、判断退款是否成立、每周汇总销售数据出优化建议等。当前现状：

- **提需求靠口头/文档，信息严重不全**：业务只说"想要个自动化"，不讲数据来源、判断规则、频率与价值，导致后续方案反复返工；
- **方案产出不统一**：不同顾问/供应商给出的方案格式、深度、口径各不相同，业务难以横向比较；
- **需求价值无排序**：需求堆积后"先做哪个"靠拍脑袋，缺乏统一的价值评估模型；
- **进度不透明**：需求提交后状态不可见，业务不知道进行到哪一步；
- **方案文档缺双视角**：只有技术方案或只有产品描述，业务（产品）与研发（技术）无法在同一份需求上对齐。

### 1.2 建设目标

建设「需求前置分析平台」，让业务人员**提交需求 → AI 前置澄清聊清楚 → 自动生成三档方案（初级/中级/高级 × 产品版/技术版）→ 价值优先级排序 → 全程进度可追溯**。

### 1.3 成功指标（KPI）

| 指标 | 目标值 | 测量方式 |
| --- | --- | --- |
| 需求画像完整度 | 澄清后平均 ≥ 85% | 平台画像完整度统计 |
| 方案返工率 | 较上线前下降 ≥ 50% | 需求评审一次通过率 |
| 需求澄清耗时 | 单需求 ≤ 15 分钟对话 | 平台澄清时长统计 |
| 方案产出效率 | 6 份文档 ≤ 5 分钟自动生成 | 平台生成耗时统计 |
| 业务满意度 | ≥ 4/5 | 评审后满意度调查 |

## 4. 功能需求（FR）

### FR1 需求提交

| 项 | 说明 |
| --- | --- |
| 描述 | 业务人员填写需求名称（必填）、一句话描述、所属部门（选填）后提交 |
| 规则 | 名称 ≤60 字；描述 ≤300 字；提交后自动生成需求编号（R-YYYYMMDD-XXX） |
| 输出 | 进入工作台列表，状态置为「已提交」，AI 自动发送首条欢迎语并引导澄清 |
| 验收 | 提交后 1 秒内出现在工作台；无名称时拦截并提示 |

### FR2 AI 前置澄清（核心）

| 项 | 说明 |
| --- | --- |
| 描述 | AI 顾问与业务对话，先把需求聊清楚：判断需求本质（单点决策/SOP流程），按《表1》《表2》框架逐步提问，边聊边提取结构化画像；支持内置引擎与混合模式两种能力（见 FR8） |
| 判定规则 | 单点决策 = 数据→分析→判断→行动（一个判断点）；SOP流程 = 多步骤串行流程；不确定时引导用户描述场景后自动判定 |
| 提问方式 | 一次只问一个问题，提供快捷选项 chips；支持用户"一次回答多条信息"，自动宽容提取（频率/价值/维度/时长/人数等） |
| 混合模式（大模型开启后） | **LLM 自主追问**：每轮由 LLM 根据当前画像自主决定问什么（规则引擎将仍缺失的标准字段作为参考传入，LLM 可追问画像外但影响方案的关键点，如合规、边界、口径、上线窗口）；**规则校验画像**：每轮回答仍由规则引擎确定性提取，画像结构与内置模式一致；**交付前自检**：标准字段齐后 LLM 对照框架审查画像，自动追问最多 5 个关键缺口（可跳过），答完才输出最终确认 |
| 覆盖字段 | 决策类：名称/部门/决策人/频率/价值/影响维度/目的/耗时/人数/输入数据(名称+来源+取数方式)/分析规则/判断标准(条件→结论→明确程度)/对应行动(结果→谁→做什么→在哪)；流程类：名称/部门/负责人/频率/价值/维度/耗时/人数/目的/步骤拆解(动作/输入/输出/触发/类型/耗时/来源/取数/靠人原因) |
| 结束条件 | 用户确认画像（"没问题"）或所有关键字段已收集；画像完整度实时显示 |
| 验收 | 典型决策需求 ≤15 轮对话完成；画像完整度 ≥85%；答非所问不写入错误字段；LLM 失败自动降级内置引擎不中断 |

### FR3 需求画像

| 项 | 说明 |
| --- | --- |
| 描述 | 澄清过程中实时生成结构化需求画像，右侧面板展示已捕获字段与完整度 |
| 规则 | 完整度按字段权重计算（决策类：频率/价值/输入数据/规则/标准/行动 等权重较高；流程类：步骤拆解权重最高） |
| 展示 | 基本信息、输入数据表、分析规则、判断标准表、对应行动表 / 步骤拆解表 |
| 验收 | 画像字段与对话内容一致；缺失项显示"待确认" |

### FR4 三档方案生成

| 项 | 说明 |
| --- | --- |
| 描述 | 按需求画像生成三档递进方案，每档含产品版 + 技术版两份文档（共 6 份） |
| 初级方案 | 1 页速览：需求定位/价值判断/关键要点表/建议下一步，快速判断"值不值得做" |
| 中级方案 | 可评审方案：背景与目标/范围/改造后流程设计/功能清单/角色分工/验收标准/建议排期 |
| 高级方案 | 完整立项文档：产品版=完整 PRD（目标/角色/流程/功能详设/数据字典/异常边界/验收KPI/里程碑）；技术版=架构/数据流/详细设计/非功能需求/实施计划/风险与回退 |
| 生成方式 | 内置引擎（模板+画像，秒级）；或大模型 API（OpenAI 兼容，skills 规则提示词，失败自动回退内置） |
| 验收 | 6 份文档全部生成；文档数据与画像一致；缺失处标注"待确认"；生成后状态自动流转为「待业务评审」 |

### FR5 方案文档查看与下载

| 项 | 说明 |
| --- | --- |
| 描述 | 详情页可在线查看每份方案文档，支持下载 Word(.docx) 与 Markdown(.md) |
| 规则 | .docx 由平台自带纯 Node 生成器产出（标题/表格/列表/引用/代码块完整保留），文件名含需求名+档位+版本 |
| 验收 | 下载的 .docx 可用 Word/WPS 正常打开，格式无错乱 |

### FR6 进度反馈

| 项 | 说明 |
| --- | --- |
| 描述 | 需求全流程状态机 + 时间线，业务随时可见"到哪一步了" |
| 状态机 | 已提交(10%) → AI前置澄清中(35%) → 画像分析中(55%) → 需求画像完成(65%) → 方案生成中(75%) → 待业务评审(90%) → 已完成(100%) |
| 记录 | 每次状态变更写入时间线（状态/备注/时间），详情页展示；业务可一键「确认完成」 |
| 验收 | 状态自动流转正确；时间线完整可追溯 |

### FR7 价值优先级分析

| 项 | 说明 |
| --- | --- |
| 描述 | AI 按统一模型给每个需求打分排序，回答"先做哪个"，并给出项目级评估 |
| 六维打分 | 价值大小 35 + 发生频率 15 + 耗时投入 15 + 影响维度 12 + 自动化潜力 15 + 参与人数 8 = 100 分 |
| 优先级 | ≥80 = P0（立即做）；60~79 = P1（本季度做）；<60 = P2（暂缓/合并） |
| 项目级评估 | 规模（≤1人月小型 / ≤3中型 / ≤6大型 / 其余超大型）、风险等级（低/中/高）、工作量人月区间（人天/22×0.8~1.3）、置信度（画像完整度≥85高 / ≥60中 / 其余低）、6 维评估（业务价值/信息完整度/自动化潜力/复杂度/集成风险/人工依赖）、待确认缺口清单 |
| 展示 | 价值优先级看板（全局排序）+ 详情页价值分析 tab |
| 验收 | 打分维度可解释；排序稳定；评估项与画像一致 |

### FR8 设置

| 项 | 说明 |
| --- | --- |
| 描述 | AI 能力来源、模型配置与数据管理 |
| AI 引擎 | ①内置引擎（零配置、离线可跑）：纯规则驱动澄清与方案生成；②混合模式（配置大模型后自动生效）：LLM 自主追问 + 规则校验画像 + 交付前自检，失败自动降级内置；两者可随时切换 |
| 数据管理 | 恢复示例数据 / 清空全部数据 |
| 验收 | 切换模式立即生效；测试连接反馈明确；大模型不可用时流程不中断 |

## 5. 系统架构（确定性编排 + 智能节点）

本平台采用「**确定性编排 + 智能节点**」的混合架构（Agentic Workflow 模式）：既保证流程**确定性**（可复现、可测试、可兜底），又具备**智能性**（理解自由语义、发现画像外缺口）。

### 5.1 分层

| 层 | 组成 | 职责 |
| --- | --- | --- |
| 规则编排层（骨架） | 澄清状态机（类型判定/字段收集/完整度/确认与收尾）、画像校验、进度状态机 | 保证流程必达、口径一致、可终止；内置引擎模式完全由本层驱动 |
| 智能节点（LLM，可选） | 自主追问节点、交付前自检节点、方案生成节点（skills 规则提示词） | 在编排层划定的节点内发挥语义理解与生成能力 |
| 兜底策略 | LLM 未配置 / 超时 / 报错 → 自动降级内置引擎 | 流程不中断 |

### 5.2 澄清环节的混合模式

- **LLM 自主追问**：每轮由 LLM 根据当前画像自主决定问什么；规则引擎将仍缺失的标准字段作为参考传入，LLM 可追问画像外但影响方案的关键点（合规、边界、数据口径、上线窗口等）；
- **规则校验画像**：每轮回答仍由规则引擎确定性提取，画像结构与内置模式完全一致，存量数据兼容；
- **交付前自检**：标准字段收集齐后，LLM 对照《表1》《表2》框架审查画像，自动追问最多 5 个关键缺口（可跳过），答完才输出最终确认。

## 6. 业务流程（端到端）

```
业务提交需求（名称/描述/部门）
   ↓
AI 前置澄清：判定类型（单点决策/SOP流程）→ 一次一问 → 提取画像
   ↓
需求画像确认（完整度 ≥85% 可生成方案；不足可跳过用"待确认"占位）
   ↓
生成三档方案：初级/中级/高级 × 产品版/技术版（6 份文档）
   ↓
自动价值分析（六维打分 + 项目级评估）→ 状态「待业务评审」
   ↓
业务评审：查看文档 → 确认完成 / 继续澄清补充
   ↓
需求进入价值优先级看板，供排期决策
```

## 7. 数据需求

### 7.1 需求实体

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 需求编号 R-YYYYMMDD-XXX |
| title / summary / department | string | 名称 / 描述 / 部门 |
| type | enum | decision（单点决策）/ sop（SOP流程）/ null（未判定） |
| status | enum | submitted/clarifying/analyzing/profiled/planning/review/done |
| statusHistory | array | 进度时间线（状态/备注/时间） |
| profile | object | 结构化需求画像（见 6.2） |
| chat | array | 澄清对话记录（角色/内容/时间） |
| plans | object | 三档方案 × 产品/技术版（Markdown + 生成时间 + 生成模式） |
| value | object | 价值分析（分数/级别/理由/评估） |

### 7.2 需求画像结构

- **单点决策**：名称、归属部门、决策人、频率、价值大小、业务影响维度、决策目的、每次耗时、参与人数、整体描述、输入数据[名称/来源系统/取数方式/备注]、分析规则、判断标准[条件/结论/明确程度]、对应行动[判断结果/谁执行/做什么/在哪操作]
- **SOP流程**：名称、归属部门、负责人、频率、价值大小、影响维度、每次耗时、涉及人数、流程目的、整体描述、步骤拆解[序号/具体动作(带角色)/输入/触发条件/步骤类型/输出/耗时/来源系统/取数方式/靠人原因]

### 7.3 字典（与《表1》《表2》一致）

| 字典 | 枚举值 |
| --- | --- |

## 8. 非功能需求（NFR）

| 类别 | 要求 |

## 10. 风险与依赖

| 风险 | 等级 | 对策 |
| --- | --- | --- |
| 业务描述信息不足，画像质量低 | 中 | 引导式提问 + 快捷选项 + 完整度提示，允许"待确认"占位 |
